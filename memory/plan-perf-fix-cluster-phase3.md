Это тот самый «рычаг 1 GPU-cull/LOD», открытый в [[project-gui-lag-gpu-bound-diagnosis]]. Статус: PLAN-only, КОД НЕ НАЧАТ (2026-07-12).

Кластеризация в плане Phase 2 стоит как «если cap недостаточен» — сначала измерить, хватает ли C1.

3. КРИТЕРИЙ РЕШЕНИЯ: если при полном наборе ламп в кадре FPS всё ещё упирается в per-fragment стоимость (растёт линейно с числом ламп в кадре, а не с локальной плотностью) — кластеризация оправдана. Если C1-кап уже даёт целевой FPS и сцены редко держат >20-30 ламп одновременно на экране — кластеризацию НЕ начинать (дорого и инвазивно), закрыть перф-трек.

ЦЕЛЬ PHASE 3: стоимость освещения фрагмента должна зависеть от ЛОКАЛЬНОЙ плотности ламп (сколько ламп реально перекрывается в точке экрана/объёма), а не от общего N. Картинка ОБЯЗАНА остаться идентичной (кластеризация только пропускает лампы, чей вклад в этот фрагмент нулевой) — это критерий корректности №1.

ДИЗАЙН (рекомендованный, от простого к полному):

ЭТАП-ПИЛОТ = 2D screen-tiled (Forward+), НЕ сразу 3D froxel — ниже риск и проще матчинг:
- Экран делится на тайлы (напр. 16x16 или 32x32 пикселя -> сетка ~120x68 при 1080p; фикс количество тайлов, напр. 32x18, надёжнее чем фикс размер).
- Для каждого тайла — БИТМАСКА uvec2 (64 бита) активных ламп. Свет i задевает тайл, если его экранный bounding-rect (проекция сферы влияния радиусом range) пересекает тайл. Битмаска -> НЕ нужен flat index-list, шейдер просто перебирает выставленные биты (findLSB/битовый цикл).
- Почему uvec2/64 бита: совпадает с дефолтным капом max_shader_lights=64. Свет за пределами 64 (slot>=64) в битмаску не влезает — поэтому битмаск-путь ПРИВЯЗАН к капу<=64. Если юзер поднимет слайдер выше — либо клэмпить кластеризацию к 64 (остальные грузить как раньше, без кластера), либо перейти на index-list вариант (offset+count в grid-буфере + flat uint-список) — это отложенное расширение, НЕ для пилота.
- Построение битмасок: CPU в irl-core, per-frame, после prioritize/flush (top-K уже отобран, slot()<64). Для каждой из <=64 ламп: спроецировать её сферу влияния в экранные координаты (MC projection*view, камера-relative позиция уже в SSBO по commit 8a6e40b), получить min/max тайлы, выставить бит во всех перекрытых тайлах. Дёшево: 64 лампы x ~несколько тайлов. Компьют-шейдер НЕ нужен при N<=64.
- Плумбинг данных: новый SSBO (или UBO) с массивом uvec2 по числу тайлов + uvec2 tileCount/tileSize в хедере. Аддитивно к существующему LightBuffer (binding 7) — НЕ ломать контракт [[addon-light-buffer-ssbo]] (96б/6xvec4, MAX_LIGHTS 2048). Взять новый свободный binding. Зарегистрировать по образцу IrlSamplers/FramePipeline.
- Шейдер (инжект в каждый пак): в точке per-light цикла (irlite_lightSurface и аналоги, см. [[shader-irlite-glsl]]) вычислить tile = ivec2(gl_FragCoord.xy)/tileSize -> прочитать uvec2 маску -> перебирать ТОЛЬКО выставленные биты вместо `for i in 0..lightCount`. Гейт под #define IRLITE_CLUSTER (как IRLITE_SHADOWS) с фолбэком «нет буфера/выключено -> цикл по всем» — тот же паттерн master-gate.

ОПЦ. ЭТАП-2 = 3D froxel (если 2D недостаточно, напр. много ламп за стеной в одном экранном столбце):
- Добавить Z-слои (лог. распределение по глубине, напр. 16-24 слоя). Froxel = tileXY x Zslice. Фрагмент маппится по gl_FragCoord.xy + линейной глубине (реконструкция viewZ из depth).
- ГЛАВНЫЙ РИСК ПЕРЕЕЗЖАЕТ СЮДА: маппинг фрагмент->Zslice в шейдере ДОЛЖЕН побайтно совпасть с тем, как мод раскидывал лампы по слоям (та же near/far и та же slice-функция). У каждого пака своя реконструкция глубины/своё gbufferProjectionInverse — сверять на этапе recon. 2D-пилот этого риска НЕ имеет (тайл = gl_FragCoord.xy/tileSize, без глубины).

RECON-ЧЕКЛИСТ (до кода, отдельным workflow, как F0 в Phase 1/2):
1. Где именно живёт per-fragment цикл по лампам в инжект-GLSL каждого пака и БАЙТ-ИДЕНТИЧЕН ли он между паками (как shadow-body в Phase 2 был идентичен — тогда правка = один шаблон на 7). Рабочая копия CR: bbs-irlights-addon/Shadres/Modification/ComplementaryReimagined/... + patches/complementaryreimagined.irlights; путь «Minecraft/Shadres/Modification» НЕ существует (дрейф-факт из [[plan-perf-fix-core-phase2]]).
2. Доступ к gl_FragCoord и разрешению кадра в точке инжекта в каждом паке (2D-тайл). Для опц. 3D — какая реконструкция viewZ/depth доступна.
3. Совпадает ли MC-projection (которой мод проецирует лампы) с проекцией главного gbuffer-прохода пака — да для мировых gbuffers (Iris юзает игровую камеру), но подтвердить на CR.
4. Свободный SSBO/UBO binding (не 7). Лимиты std430.
5. Взаимодействие с VL-маршем: каждый шаг луча — своя глубина/froxel. Решить: VL держит полный (уже капнутый) список как сейчас (VL-шаги — доминанта per-light, уже урезаны в Phase 1), ИЛИ per-segment грубый кластер. Для пилота — VL НЕ трогать (только surface-цикл), это и есть P0.

ПЛАН РЕАЛИЗАЦИИ (пилот, порядок):
A. irl-core: построитель битмасок (проекция сферы->экранный rect->set bits), upload-буфер, конфиг-тоггл + размеры сетки. Редактор ДОЛЖЕН компилиться против нового core (проверять как в Phase 2). Ревью adversarial (корректность проекции/консерв. границы тайла).
B. Шейдер CR-ПИЛОТ (только CR, как Phase 1): #define IRLITE_CLUSTER + маппинг тайла + masked-цикл в surface-пути; фолбэк на полный цикл. Реген патча (gen-complementary-patch.ps1) + PatchHarness byte-валидация (apply==Modification) + run-пак синк (md5). См. [[sync-workflow]].
C. Замер + КОРРЕКТНОСТЬ: A/B кластер on/off на стресс-сцене. (1) картинка ПИКСЕЛЬ-в-пиксель идентична (это гейт — кластер не имеет права менять свет; дать image-gen EXPECTED/REGRESSION по [[feedback-visual-test-image-prompts]]); (2) FPS вверх при многих лампах, и рост стоимости с ЛОКАЛЬНОЙ плотностью, а не с общим N.
D. ТИРАЖ на остальные 6 паков (bliss/bsl/photon/rethinkingvoxels/solas/iterationrp) — строго по прямой команде юзера, если surface-цикл байт-идентичен CR (один шаблон). IterationRP остаётся локальным/gitignored (см. историю в [[project-point-shadow-fix-backlog]]).

КРИТЕРИИ И РИСКИ:
- КОРРЕКТНОСТЬ (гейт): консервативная граница тайла (лампа на границе rect не должна выпасть — добавить slack в 1 тайл), иначе тёмные швы по границам тайлов. Проекция сферы влияния радиусом range (для спота — та же сфера консервативно, конус не сужать).
- Если картинка расходится с наивным режимом — баг проекции/маппинга, НЕ «оптимизация»; чинить до замера FPS.
- Кап>64: битмаск-путь ломается — либо клэмп к 64, либо index-list (отложено).
- 3D froxel Z-slice mismatch мод<->шейдер = главный риск полной версии; пилот 2D его избегает.
- НЕ ломать: SSBO-контракт binding7, #define-контракты, якоря патчей, shadow-стек (Phase 1/2 фильтрация цела).
